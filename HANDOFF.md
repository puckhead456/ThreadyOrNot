  - **3D follow mode** (`docs/wave-f/3d-follow.md`). Each stitch tap turns the piece by 360°/count of the round being worked (10° on 36), so the stitch just made faces you; 36 taps on 36 are exactly one turn and the next round carries on from the seam. The angle is absolute (2π·index/count, walked through the round's real slice widths), so Undo, un-tapping a row and a jump from the pattern sheet all re-aim instead of drifting. The turn eases over 150 ms (up to 420 for a long swing) and snaps under reduced motion. A swipe still spins freely; the next tap blends back the short way. Between taps nothing moves and nothing is drawn. A rows-mode sheet wider than the frame slides to keep the working stitch centred. A finished piece turns slowly as a trophy. ## How to work on it

- Local server: `.claude/launch.json` config `stitchkeeper` runs `tools/serve.ps1` on http://localhost:8765 (no node or python on this machine); the `wave-1` worktree's config `wave1` serves http://localhost:8766. Use the Browser pane's preview tools, never Bash, to run it. **The dev server answers only `Host: localhost`**: 127.0.0.1 and `*.localhost` get 400, so there is no second origin to give an agent private storage (use `Store.__setKeyForTests`, below).
- **Caching / service worker** (rewritten 2026-09-18; no more manual bumps, no more clearing ritual):
  - `CACHE_VERSION` in `sw.js` is **generated, never hand-edited**. `tools/sw-version.sh` (Git Bash) hashes every file in `PRECACHE_URLS` — the list is read out of `sw.js` itself — plus `sw.js` minus the version line, and rewrites the line in place (`h<10 hex>`), printing old → new. It is idempotent. `--check` verifies without writing, `--list` prints the precached paths.
  - Run **once per clone**: `git config core.hooksPath .githooks` (already done in this working copy). `.githooks/pre-commit` then regenerates and re-stages `sw.js` whenever a precached file is staged. The hook file must stay LF-only (a CRLF shebang breaks it on Windows); if a fresh clone mangles it, `git config core.autocrlf input` or the `.gitattributes` fix.
  - The deploy is gated: `.github/workflows/pages.yml` runs `bash tools/sw-version.sh --check` before uploading and fails the job if `sw.js` disagrees with the content hash. The hook can be skipped; the gate cannot.
  - **On localhost / 127.0.0.1 the SW precaches nothing and is network-first for everything same-origin** (cache is an offline fallback only, and `activate` deletes every cache). You do **not** need to unregister the worker or clear caches before testing — just reload. Still a new file? Hard-reload once.
  - In production, same-origin requests are **stale-while-revalidate**: the cached copy is served instantly and refreshed in the background, so even a missed version bump heals on the next load. Navigation stays network-first (cached `index.html` when offline), Google Fonts stay SWR. Only precached paths and `icons/` are ever written to the cache; **`/tmp-pdf/` and `/test/` are never cached on any host**, so a swapped fixture PDF is always read fresh.
  - New file that must work offline → add it to `PRECACHE_URLS` in `sw.js`; the hash and the version follow automatically.
  - `test/sw.test.html` (29 assertions) covers the routing decision: it fetches `sw.js` as text and runs its pure `swPolicy` against a fake production location and a fake localhost one, so both stories are checked without registering anything. Since wave F it also fails when a `<script src>` in `index.html` is missing from `PRECACHE_URLS`.
  - On a deploy, `index.html`'s registration script shows a non-blocking "A new version is ready — Reload" toast (falls back to a `.sw-update` banner if `App.toast` is not up) and calls `registration.update()` on `visibilitychange`, at most once per 10 minutes. It never auto-reloads.
- Browser pane quirks: the service worker will not register inside the pane (environment, not code); `requestAnimationFrame` is throttled unless a screenshot forces a frame, so take a cheap screenshot before driving a canvas with synthetic pointer events; `window.open` is blocked (the printable chart's blob-URL fallback is what you will exercise). The pane's localStorage is a scratch profile: agents may wipe it. The owner's phone data is separate.
- **The pane's storage is shared by every tab and every agent** (learned in wave E). localStorage is one profile: a store-safety or backup run in another tab resets it, so in-app checks made while those suites run lose their projects mid-import. The fixture pages cache each PDF's extracted text in **sessionStorage**, which lives as long as the tab: after an extractor change, open the fixture page in a **fresh tab** (`tabs_create`) or it keeps testing the old extraction.
- **Private state for in-app checks** (learned in wave F): in your own tab, `Store.__setKeyForTests('stitchkeeper-<your-name>')` points the store at its own localStorage key and reloads from it, so projects you make survive other agents' test pages resetting the shared profile. It is test-only (never called by app code). BlobStore (IndexedDB) is still shared: delete your projects and their `p:<id>:` images when done, remove the key, and never wipe the whole store, which destroys other agents' scratch work mid-task.
- **pdf.js cannot draw pages while the pane is hidden.** Page rendering waits on `requestAnimationFrame`, which never fires in a hidden pane, so a page render (cross-stitch chart pages, sewing page images, `test/pdftext.test.html`'s one frame-dependent case, which then skips) stalls until the pane is shown. Screenshots time out too. Show the pane, or shim rAF with `setTimeout` in your own tab only (never in source); text extraction is unaffected.
- **The fixture pages re-extract through `PdfText`**, so a change to `js/pdftext.js` can turn any parser suite red (patterns, xstitch and sewing fixtures all did, mid-wave). When a parser suite goes red with no parser change, look at the extractor first, and re-run the parser fixture pages (fresh tab) after every extractor change. Since wave H that includes `test/knits.fixtures.html` and the real-page groups of `test/knit-chart.test.html`; and since `js/knits.js` is built on the `js/patterns.js` engine, a change to `patterns.js` must re-run the knitting suites as well as the crochet ones (and a change to `knits.js` must leave patterns 1037 / patterns.fixtures 829 untouched). A suite run in the middle of another agent's save can also fail transiently; let the file sit, then re-run.
- Git: signed in; pushes work non-interactively with `GIT_TERMINAL_PROMPT=0 GCM_INTERACTIVE=never`. Put commit messages in a short-path file such as `C:\Users\mitch\AppData\Local\Temp\sk-commit.txt` and use `git commit -F`; long scratchpad paths break git on Windows. Git Bash heredocs work; PowerShell here-strings with quotes do not survive as git arguments. End commit messages with the Co-Authored-By line.
- Deploy = push to `main` (single branch; the owner wants everything on main). Verify live files WITHOUT cache-busting query strings (GitHub's CDN returns 404 for `?x=` on fresh deploys); polling `sw.js` for the new `CACHE_VERSION` (now a generated `h…` hash — `bash tools/sw-version.sh --print` tells you what to expect) is the reliable check.
- Delegation pattern that has worked: write the contract (SPEC.md / CRAFTS.md), spawn one Opus agent per independent file group with strict file ownership, tell each to use its own Browser-pane tab (`tabs_create` + `tabId`), integrate, run every test page, verify at 375×812, deploy (the cache version regenerates itself). Research-first for new crafts (one agent writes `docs/research/<craft>.md`, then builders implement Part B).
- Coordinating a wave (as waves E, F and H did; wave H added a binding `docs/wave-h/CONTRACT.md` because its six workers built against each other's names, and each "Contract changes" section in a report records a deviation from it): one shared brief (`docs/wave-e/BRIEF.md`: worktree, ownership, baseline counts, "every fix gets an assertion"), and each worker writes `docs/wave-<x>/<name>.md` (discrepancy table, rules added, still wrong, "For the owner of <file>" notes, decisions for the coordinator) instead of touching `HANDOFF.md` / `SPEC.md` / `CRAFTS.md`; a docs agent integrates afterwards. Cross-file requests travel through those "For the owner of" sections. **On any file another agent may be editing, use Edit (string replacement), never Write**, so concurrent edits to other regions survive (`js/store.js` and `test/diagram.test.html` were each shared by two agents in wave E).
