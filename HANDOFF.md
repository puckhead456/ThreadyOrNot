# Handoff: Thready or Not

Crochet, knitting, cross-stitch and sewing counter PWA. Live: https://puckhead456.github.io/ThreadyOrNot/ (repo puckhead456/ThreadyOrNot, deploys from `main` via `.github/workflows/pages.yml`, ~1 minute). Local folder `C:\Users\mitch\CrochetBs` (folder name intentionally unchanged). Plain HTML/CSS/JS, **no build step, no modules, no framework**; one `window` global per file from an ES5 IIFE. Owner: puckhead456 (Windows user "mitch"). Started 2026-09-14; crafts expansion 2026-09-15/16.

Read in this order: this file → `SPEC.md` (crochet + shell contract; the "Crafts" section points onward; "Wave K: every craft as rich as crochet" for what each craft does now) → `docs/CRAFTS.md` (the craft plugin contract, with "Wave K: shared surfaces") → `docs/wave-k/api/*.md` when you touch a wave K file → `docs/research/cross-stitch.md` and `docs/research/sewing.md` (research + the per-craft specs the modules were built from; the code is the truth where they differ) → `docs/research/knitting.md` (the knitting fixtures' ground truth, wave H).

## How to work on it

- **Run the suites headless (wave K).** From the worktree, with the dev server up on 8766:
  `TIMEOUT=600 SHOW_TIME=1 bash tools/headless-suite.sh --all` runs every `test/*.html` that has a
  `#summary` with a "N passed, M failed" line (38 pages, about 5 minutes; `ocr.fixtures` alone takes
  ~170–200 s, which is why `TIMEOUT=600`: the default is 180 s). Name pages to run a few
  (`bash tools/headless-suite.sh sewing.test 'sew-visual.test?real=1'`). **Real time is the
  default**: `tools/cdp-page.ps1` starts headless Chrome (Edge if Chrome is missing) with a throwaway
  profile and polls `#summary` over the DevTools protocol, so pdf.js, IndexedDB, WebGL and Workers
  all run (the old virtual-time path, `VIRTUAL=1`, cannot run PDF or IndexedDB pages and gives
  false reds). `JOBS=3` pages at once by default (`JOBS=1` to re-run a red page alone: the
  wall-clock budgets in `xstitch-read` and `xstitch` go red under load); `DUMP=<dir outside the
  repo>` saves each page's text so `grep '^FAIL' <dir>/*.txt` lists the failed assertions. It
  exits non-zero on any red, timeout or missing summary, and kills only its own browsers.
  Details and the per-page table: `docs/wave-k/suites.md`.
- **The Browser pane is for looking, not for running suites.** It runs out of tabs with more than
  five or six agents; open one tab when you need to see the real UI and close it. **Agents' pane
  screenshot prompts may be declined by the owner**: take headless screenshots instead
  (`chrome.exe --headless=new --window-size=375,812 --screenshot=<png in your temp dir> <url>`;
  headless Chrome will not lay out under ~500 px, so the test pages offer a phone frame:
  `xstitch-extras.test.html?phone=375x812&demo=<id>`, `sewing-extras.test.html?frame=375x812`,
  `knit-ui.shots.html?scene=…`). Never write screenshots into the repo.
- Local server: `.claude/launch.json` config `stitchkeeper` runs `tools/serve.ps1` on http://localhost:8765 (no node or python on this machine); the `wave-1` worktree's config `wave1` serves http://localhost:8766. Use the Browser pane's preview tools, never Bash, to run it. **The dev server answers only `Host: localhost`**: 127.0.0.1 and `*.localhost` get 400, so there is no second origin to give an agent private storage (use `Store.__setKeyForTests`, below).
- **Caching / service worker** (rewritten 2026-09-18; no more manual bumps, no more clearing ritual):
  - `CACHE_VERSION` in `sw.js` is **generated, never hand-edited**. `tools/sw-version.sh` (Git Bash) hashes every file in `PRECACHE_URLS` — the list is read out of `sw.js` itself — plus `sw.js` minus the version line, and rewrites the line in place (`h<10 hex>`), printing old → new. It is idempotent. `--check` verifies without writing, `--list` prints the precached paths.
  - Run **once per clone**: `git config core.hooksPath .githooks` (already done in this working copy). `.githooks/pre-commit` then regenerates and re-stages `sw.js` whenever a precached file is staged. The hook file must stay LF-only (a CRLF shebang breaks it on Windows); if a fresh clone mangles it, `git config core.autocrlf input` or the `.gitattributes` fix.
  - The deploy is gated: `.github/workflows/pages.yml` runs `bash tools/sw-version.sh --check` before uploading and fails the job if `sw.js` disagrees with the content hash. The hook can be skipped; the gate cannot.
  - **On localhost / 127.0.0.1 the SW precaches nothing and is network-first for everything same-origin** (cache is an offline fallback only, and `activate` deletes every cache). You do **not** need to unregister the worker or clear caches before testing — just reload. Still a new file? Hard-reload once.
  - In production, same-origin requests are **stale-while-revalidate**: the cached copy is served instantly and refreshed in the background, so even a missed version bump heals on the next load. Navigation stays network-first (cached `index.html` when offline), Google Fonts stay SWR. Only precached paths and `icons/` are ever written to the cache; **`/tmp-pdf/` and `/test/` are never cached on any host**, so a swapped fixture PDF is always read fresh.
  - New file that must work offline → add it to `PRECACHE_URLS` in `sw.js`; the hash and the version follow automatically.
  - `test/sw.test.html` (29 assertions) covers the routing decision: it fetches `sw.js` as text and runs its pure `swPolicy` against a fake production location and a fake localhost one, so both stories are checked without registering anything. Since wave F it also fails when a `<script src>` in `index.html` is missing from `PRECACHE_URLS`.
  - On a deploy, `index.html`'s registration script shows a non-blocking "A new version is ready — Reload" toast (falls back to a `.sw-update` banner if `App.toast` is not up) and calls `registration.update()` on `visibilitychange`, at most once per 10 minutes. It never auto-reloads.
- Browser pane quirks: the service worker will not register inside the pane (environment, not code); `requestAnimationFrame` is throttled unless a screenshot forces a frame, so take a cheap screenshot before driving a canvas with synthetic pointer events; `window.open` is blocked (the printable chart's blob-URL fallback is what you will exercise). The pane's localStorage is a scratch profile: agents may wipe it. The owner's phone data is separate.
- **The pane's storage is shared by every tab and every agent** (learned in wave E). localStorage is one profile: a store-safety or backup run in another tab resets it, so in-app checks made while those suites run lose their projects mid-import. The fixture pages cache each PDF's extracted text in **sessionStorage**, which lives as long as the tab: after an extractor change, open the fixture page in a **fresh tab** (`tabs_create`) or it keeps testing the old extraction.
- **Private state for in-app checks** (learned in wave F): in your own tab, `Store.__setKeyForTests('stitchkeeper-<your-name>')` points the store at its own localStorage key and reloads from it, so projects you make survive other agents' test pages resetting the shared profile. It is test-only (never called by app code). BlobStore (IndexedDB) is still shared: delete your projects and their `p:<id>:` images when done, remove the key, and never wipe the whole store, which destroys other agents' scratch work mid-task.
- **pdf.js cannot draw pages while the pane is hidden.** Page rendering waits on `requestAnimationFrame`, which never fires in a hidden pane, so a page render (cross-stitch chart pages, sewing page images, `test/pdftext.test.html`'s one frame-dependent case, which then skips) stalls until the pane is shown. Screenshots time out too. Show the pane, or shim rAF with `setTimeout` in your own tab only (never in source); text extraction is unaffected.
- **The fixture pages re-extract through `PdfText`**, so a change to `js/pdftext.js` can turn any parser suite red (patterns, xstitch and sewing fixtures all did, mid-wave). When a parser suite goes red with no parser change, look at the extractor first, and re-run the parser fixture pages (fresh tab) after every extractor change. - **Running a wave this size (learned in wave K, about twenty workers over four 5-hour windows;
  `docs/wave-k/STATUS.md` is the log).**
  - **Pace against the session limit.** Ten Opus agents burned about 2.2 points of the 5-hour limit
    a minute, so a full window bought roughly 40–45 minutes of ten-agent work. Check with
    `mcp__ccd_session_mgmt__get_usage`; plan batches to the window; the owner's rule moved from
    "pause at 95 %" to "run to 100 %" mid-wave. Write the "if the limit cuts this window off" plan
    into the status file before it runs out (agents to resume, by id, and what each was doing).
  - **Pause and resume by `SendMessage`.** A stopped agent keeps its context: resume it with
    "continue from where you stopped; re-read BUILD.md; re-run your suites first, other workers'
    files changed". Restart the dev server after a reset (tab ids are gone). Tell workers to
    **finish cleanly rather than widely**: land what is green, keep the report current, then go on.
  - **Backup refs, not commits, mid-wave.** The worktree stayed uncommitted while suites could be
    red; snapshots were saved as `refs/backup/wave-k-0200`, `refs/backup/wave-k-0305` and
    `refs/backup/wave-k-w4-start` (no branch moved, no hooks run). Restore one file with
    `git checkout refs/backup/wave-k-0305 -- <path>`.
  - **Publish the interface first.** Every worker wrote `docs/wave-k/api/<name>.md` in its first
    minutes; others built against it and feature-detected anything not there yet. Batch 2 started
    only when the batch-1 API files it needed existed.

    resumed eight times (OCR wiring, Whole piece, `surfaceUnderHud`, knitting hooks, the book
    import, materials, `setDone`), sew-core and knit-parse twice, xs-core, xs-read and

    CSS and tests) to look at the screens on real fixtures, add app-level tests and fix; the
    builder never touched them again.
  - **Split a craft's screen in two** so two workers never share a file: the app file (chart /
    step screen, working mode, import) and an extras file behind the fixed `menuItems` / `open`
    contract (`docs/CRAFTS.md` → "Extras modules"). The coordinator created the placeholders first.
